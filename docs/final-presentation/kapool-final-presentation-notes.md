# KAPOOL 최종 발표 발표자 노트

## 1. 군산대학교 통학 카풀 웹 기반 예약 및 운행 관리 시스템

최종 발표의 시작입니다. 중간발표에서 정의했던 카카오톡 오픈채팅 기반 문제를 실제 웹 시스템으로 어떻게 개선했는지 설명합니다. 특히 이번 발표는 기능 결과물뿐 아니라 네트워크 수업 관점에서 요청, 응답, 인증, 데이터 저장, 실시간 통신 흐름을 중심으로 다룹니다.

## 2. 현재 카풀 운영 방식

기존 방식은 차주와 승객을 빠르게 연결할 수 있다는 장점은 있지만, 모든 정보가 채팅 메시지 형태로 흘러갑니다. 사용자가 조건을 입력하고 서버가 결과를 반환하는 요청-응답 구조가 약합니다. 그래서 정보 조회보다 채팅을 계속 스크롤해야 하는 방식이 됩니다.

## 3. 정보가 채팅 흐름에 묻힘

이 문제는 단순히 UI가 불편한 문제가 아닙니다. 네트워크 관점에서는 서버가 운행 정보를 구조화해서 저장하고, 사용자가 조건 기반으로 조회할 수 있는 API 구조가 없다는 의미입니다. 즉 정보가 네트워크 서비스의 데이터가 아니라 대화방의 텍스트로만 존재합니다.

## 4. 경로와 운행 정보의 비구조화

예를 들어 “오늘 17시 전주 호남제일문에서 군산대 갑니다”라는 문장은 사람에게는 의미가 있지만 서버가 안정적으로 처리하기 어렵습니다. 최종 구현에서는 from, to, departureTime, seats, fare, waypoints 같은 필드로 운행을 저장하도록 바꿨습니다.

## 5. 예약 상태와 정산 상태 동기화 문제

카풀 서비스에서는 예약, 좌석, 정산 상태가 서로 연결됩니다. 승인이 되면 좌석 수가 줄어야 하고, 운행 이후 정산 상태도 기록되어야 합니다. 이런 상태 동기화는 채팅만으로는 어렵고, 서버와 데이터베이스가 중심이 되어야 합니다.

## 6. Project Goal

프로젝트 목표는 기존 소통 방식을 완전히 버리는 것이 아니라, 카풀에 필요한 핵심 정보를 구조화하는 것입니다. 지역, 시간, 경로를 데이터 모델로 만들고, 검색과 예약, 사용자 식별, 운행 단위 소통이 가능하도록 했습니다.

## 7. 전체 시스템 구조

전체 구조는 클라이언트-서버-데이터베이스 3계층 구조입니다. React 웹은 직접 DB에 접근하지 않고 NestJS API 서버에 요청합니다. API 서버는 비즈니스 로직을 처리하고 Prisma를 통해 PostgreSQL과 통신합니다. 실시간 채팅은 Socket.IO Gateway가 담당합니다.

## 8. HTTP Request / Response 흐름

HTTP는 요청이 있어야 응답이 오는 구조입니다. 예를 들어 사용자가 운행 목록을 열면 React에서 GET /rides 요청을 보냅니다. 서버는 Controller, Service, Prisma, PostgreSQL을 거쳐 JSON 형태로 응답하고, 클라이언트는 그 데이터를 화면에 렌더링합니다.

## 9. Bearer Token 기반 인증과 권한

로그인 후 서버는 HMAC 기반 JWT-like 토큰을 발급합니다. 클라이언트는 이 토큰을 저장하고, 보호된 API를 호출할 때 Authorization 헤더에 넣어 보냅니다. 서버는 토큰을 검증한 뒤 passenger, driver, admin 역할에 따라 예약 신청, 운행 등록, 신고 관리 접근을 제어합니다.

## 10. 로그인 / 메인 / 운행 조회

중간발표에서는 로그인과 메인 화면이 중심이었지만, 최종 결과에서는 실제 API 연동이 반영되었습니다. 로그인 후 토큰을 통해 세션을 확인하고, 운행 목록은 서버에서 JSON으로 받아옵니다. 이는 기존 채팅방 스크롤 대신 서버 기반 조회 흐름으로 바뀐 부분입니다.

## 11. 차주 중심 운행 등록

운행 등록은 차주의 자유 텍스트 공지를 표준 입력 형식으로 바꾸는 기능입니다. 서버는 이 데이터를 Ride, Vehicle과 연결해 저장합니다. 결과적으로 운행 정보가 검색과 예약에 사용할 수 있는 데이터가 됩니다.

## 12. 예약 신청과 상태 전이

예약은 pending에서 시작해 approved, rejected, cancelled, completed로 전이됩니다. 특히 승인 시에는 단순히 상태만 바꾸는 것이 아니라 남은 좌석 수를 줄이고 정산 레코드를 생성합니다. 이것이 서버와 DB 기반 상태 동기화의 핵심입니다.

## 13. HTTP + WebSocket 기반 실시간 채팅

채팅은 두 가지 네트워크 방식을 함께 사용합니다. 처음 채팅방에 들어갈 때 기존 메시지는 HTTP로 조회하고, 이후 실시간 메시지는 WebSocket 연결로 주고받습니다. WebSocket은 연결을 유지하기 때문에 서버가 새 메시지를 즉시 참여자에게 보낼 수 있습니다.

## 14. 신고와 관리자 검토 흐름

정산 누락이나 부적절한 채팅 같은 문제는 신고 데이터로 남깁니다. 관리자는 신고 목록과 연결된 운행, 예약, 결제, 채팅 맥락을 확인하고 상태를 바꿀 수 있습니다. 기존 오픈채팅에서 관리자 확인이 어려웠던 부분을 데이터 기반 관리 흐름으로 개선했습니다.

## 15. 최종 구현 결과 정리

최종 결과는 비정형 메시지 운영을 구조화된 네트워크 시스템으로 전환한 것입니다. 운행은 API로 조회되고, 예약과 정산 상태는 DB에 저장되며, 실시간 소통은 WebSocket으로 처리됩니다. 네트워크 프로젝트 관점에서는 요청-응답, 인증, 상태 동기화, 실시간 통신을 하나의 서비스 흐름 안에 구현한 결과입니다.
